> 💡 **이 글에서 답하는 질문**  
> "ACID는 왜 4개일까? 셋이면 안 되나?"  
> "Dirty Read, Phantom Read는 왜 \"읽기\" 문제인가? 쓰기가 아니라?"  
> "락(Lock)과 MVCC는 결국 같은 일을 하는 건가?"

## 1. 평범한 이체 한 줄

은행 시스템에서 A씨가 B씨에게 1만 원을 보낸다. 코드 수준에서는 이 \"하나의 일\"이 사실 두 개의 SQL이다.

```sql
-- ① A의 잔액에서 1만 원 출금
UPDATE 계좌 SET 잔액 = 잔액 - 10000 WHERE 계좌번호 = 'A';

-- ② B의 잔액에 1만 원 입금
UPDATE 계좌 SET 잔액 = 잔액 + 10000 WHERE 계좌번호 = 'B';
```

A의 잔액이 10만 원, B의 잔액이 5만 원이라 하자. 정상이라면 ①+② 후 A=9만, B=6만. 시스템 전체의 \"총잔액 15만\"은 유지된다.

그런데 다음 네 가지 상황이 우리를 기다리고 있다.

## 2. 시나리오 ① — 절반만 성공한다면? (원자성)

① 출금까지 끝났는데 ② 입금 직전에 **서버가 죽었다**.

```
A: 10만 - 1만 = 9만 ✓ 저장됨
B: 5만 + 1만 = 6만 ✗ 실행 못 함
```

A의 1만 원은 사라졌고, B는 받지 못했다. **총잔액이 14만**으로 줄었다. 누군가의 돈이 증발했다.

이 비극을 막으려면 \"두 작업이 **하나의 단위**\" 라는 약속이 필요하다.

> **Atomicity (원자성)**: 트랜잭션 안의 모든 작업이 **다 성공하거나 다 실패**. 부분 성공은 없다.

DBMS는 이걸 어떻게 보장할까? **트랜잭션 로그**(Oracle의 REDO/UNDO, MySQL의 binlog/InnoDB log)를 쓴다.

- ①을 실행하기 전, \"A의 원래 값은 10만이었다\"를 **UNDO 로그**에 적는다.
- ②를 실행하기 전, \"B의 원래 값은 5만이었다\"를 UNDO 로그에 적는다.
- 마지막에 `COMMIT`이 끝나야 \"이 트랜잭션은 확정\".
- 도중에 죽으면, DBMS가 재시작 시 UNDO 로그를 보고 \"A를 10만으로 되돌려라\"를 실행한다.

> 💡 그래서 \"트랜잭션을 시작했으면 반드시 COMMIT 또는 ROLLBACK\"이라는 말이 나온다. 미결 상태로 두면 락도 풀리지 않고 데이터도 어정쩡하다.

## 3. 시나리오 ② — 음수 잔액이 가능한가? (일관성)

A의 잔액이 5천 원인데 1만 원을 보내려 한다. 출금하면 잔액이 -5천 원이 된다.

여기서 두 가지 해석이 있다.

1. **계좌 잔액은 음수가 될 수 없다**는 비즈니스 규칙(CHECK 제약, 트리거)이 있다면, DBMS가 ①을 거부한다 → 트랜잭션 ROLLBACK. 일관성 유지.
2. 규칙이 없다면 -5천 원으로 저장된다. 데이터는 무결성 측면에서 \"DBMS 규칙\"은 안 깨졌지만, **비즈니스 일관성**은 깨졌다.

> **Consistency (일관성)**: 트랜잭션 전후에 **모든 무결성 제약**이 유지된다.

여기서 \"무결성\"이라는 단어가 묘하다. 일관성은 사실 **개체·참조·도메인·사용자 정의 무결성**을 모두 포함한다.

- **개체 무결성**: PK는 NULL/중복 불허용
- **참조 무결성**: FK는 참조 대상이 실재해야
- **도메인 무결성**: 컬럼이 정의된 타입·범위 안의 값만
- **사용자 정의 무결성**: CHECK 제약, 트리거로 표현되는 업무 규칙

> 📌 ACID 중 일관성은 **DBMS만의 책임이 아니다**. 개발자가 제약을 잘 걸어야 한다. 트랜잭션은 \"제약을 지킨 상태에서 다음 상태로 옮겨주는 도구\"일 뿐.

## 4. 시나리오 ③ — 두 이체가 동시에? (고립성)

A의 잔액이 10만 원이다. 두 트랜잭션이 동시에 \"A에서 7만 원씩 출금\"을 시도한다.

```
T1: SELECT 잔액 FROM 계좌 WHERE 계좌번호='A';       -- 10만 읽음
T2: SELECT 잔액 FROM 계좌 WHERE 계좌번호='A';       -- 10만 읽음
T1: UPDATE 계좌 SET 잔액 = 10만 - 7만 WHERE ...;    -- A = 3만 저장
T2: UPDATE 계좌 SET 잔액 = 10만 - 7만 WHERE ...;    -- A = 3만 저장
```

결과: A=3만. 그러나 총 14만이 빠져나갔다. **A는 -4만이어야 정상**. 사라진 4만 원은 두 트랜잭션이 \"같은 출발점\(10만\)\"에서 따로 계산했기 때문에 사라졌다 (Lost Update).

이런 동시성 사고를 4가지로 분류한다.

| 현상 | 무엇이 일어나는가 |
|---|---|
| **Dirty Read** | T1이 **미커밋** 값을 변경했는데 T2가 그 값을 읽는다. T1이 롤백하면 T2는 존재하지 않는 값을 본 셈. |
| **Lost Update** | 위 시나리오. 두 트랜잭션이 같은 행을 동시 갱신해 한쪽이 \"잊혀짐\". |
| **Non-repeatable Read** | T1이 같은 행을 두 번 읽었는데 사이에 T2가 갱신해서 값이 다르다. |
| **Phantom Read** | T1이 \"조건에 맞는 행 수\"를 두 번 셌는데, 사이에 T2가 INSERT해서 행 수가 늘었다. |

이 문제들을 막는 두 가지 접근이 있다.

### 4-1. 락 (Lock) — 비관적 동시성 제어

\"누가 건드릴까 봐 미리 막아둔다\"는 발상.

- **공유락(S)**: 읽기 허용, 쓰기 차단. 여러 트랜잭션이 동시 S 가능.
- **배타락(X)**: 읽기·쓰기 모두 차단. 한 번에 한 트랜잭션만.

T1이 A 행에 X락을 잡으면, T2는 A 행에 어떤 락도 못 잡고 **대기**한다. T1이 COMMIT하고 락을 풀면 T2가 잡는다.

문제는 **데드락**과 **성능**.

```
T1: A에 X락 → B에 X락 대기
T2: B에 X락 → A에 X락 대기
   → 영원히 대기 (Deadlock)
```

DBMS가 데드락을 감지하면 **한쪽을 강제 ROLLBACK**한다.

### 4-2. MVCC — 낙관적 동시성 제어

\"각 트랜잭션은 **자기만의 스냅샷**을 본다\"는 발상.

- T1이 시작하면 그 시점의 데이터 버전을 본다.
- 그 사이 T2가 같은 행을 갱신해도, T1은 여전히 **자기 버전**을 본다.
- 충돌은 COMMIT 시점에 검증한다.

Oracle·PostgreSQL이 기본으로 채택. 락 없이도 \"읽기는 쓰기를 막지 않고, 쓰기는 읽기를 막지 않는\" 마법 같은 동작이 가능하다.

> 💡 **그래서 어떻게 됐냐면**: 대부분의 현대 DBMS는 **락 + MVCC를 혼용**한다. 일반 SELECT는 MVCC, 갱신·잠금 SELECT(`FOR UPDATE`)는 락. SQL Server는 기본 락 모드지만 \"Read Committed Snapshot\" 옵션을 켜면 MVCC도 가능.

### 4-3. 격리 수준 4단계

\"얼마나 엄격하게 막을지\"를 사용자가 고를 수 있다.

| 격리 수준 | Dirty | Non-repeatable | Phantom | 대표 DBMS 기본 |
|---|---|---|---|---|
| READ UNCOMMITTED | ⚠️ | ⚠️ | ⚠️ | (거의 안 씀) |
| READ COMMITTED | ✓ | ⚠️ | ⚠️ | Oracle, PostgreSQL |
| REPEATABLE READ | ✓ | ✓ | ⚠️ | MySQL InnoDB |
| SERIALIZABLE | ✓ | ✓ | ✓ | (가장 안전·가장 느림) |

\"✓\"는 차단, \"⚠️\"는 발생 가능.

엄격할수록 **안전하지만 느려진다**. 대부분의 OLTP 시스템이 READ COMMITTED를 쓰는 이유다.

> **Isolation (고립성)**: 동시에 실행되는 트랜잭션은 **서로 영향을 주지 않는 듯** 동작해야 한다. 단, \"얼마나 그렇게 보이게 할지\"는 격리 수준으로 조절.

## 5. 시나리오 ④ — 정전이 나도 살아남는가? (지속성)

①+② 둘 다 성공하고 COMMIT까지 끝났다. 그 직후 데이터센터에 정전이 발생한다.

다시 켰을 때, A=9만 / B=6만이 그대로 있어야 한다. 만약 \"COMMIT은 됐지만 디스크에 못 적었다\" 면? 데이터가 날아간다.

DBMS는 COMMIT 시점에 다음을 보장한다.

1. **REDO 로그**가 **디스크에 기록**되어 있다 (\"이 트랜잭션은 적용해야 함\"이라는 기록).
2. 실제 데이터 페이지는 메모리에만 있어도 OK. 정전 후 재시작 시 REDO 로그를 보고 \"이건 적용해라\"를 다시 실행한다.

이걸 **WAL (Write-Ahead Logging)** 이라 한다. \"로그를 먼저 디스크에 적고, 데이터 페이지는 나중에 적어도 된다\"는 규칙. 디스크 쓰기 부하를 크게 줄여준다.

> **Durability (지속성)**: 한 번 COMMIT된 데이터는 **시스템 장애가 나도 영구 보존**.  
> 구현 방식: REDO 로그 + 백업 + 복제.

## 6. ACID는 \"네 개로 나뉘어 있어야 했다\"

이제 정리해보면 ACID는 임의로 정한 네 단어가 아니라, **데이터가 깨지는 네 가지 방향에 대한 답**이다.

| 단어 | 답하는 질문 | 구현 |
|---|---|---|
| **A**tomicity | \"중간에 죽으면?\" | UNDO 로그 + ROLLBACK |
| **C**onsistency | \"규칙 위반이 들어오면?\" | 제약조건 + 트리거 |
| **I**solation | \"동시에 둘이 건드리면?\" | Lock + MVCC + 격리 수준 |
| **D**urability | \"정전이 나면?\" | REDO 로그 + WAL + 백업 |

이 중 하나라도 빠지면 \"이게 정말 데이터베이스인가\" 의심받을 만한 사고가 난다. 그래서 RDBMS의 가장 기본 약속이 ACID다.

## 7. NoSQL은 ACID를 \"포기\"한 게 아니다

종종 \"NoSQL은 ACID 대신 BASE\"라는 말을 듣는다. BASE는 **Basically Available, Soft state, Eventually consistent**의 줄임.

핵심은 **\"분산\"** 이다. 데이터가 100대 서버에 흩어져 있을 때, \"세계 모든 곳에서 즉시 같은 답이 나오는 일관성\"은 비싸다. CAP 정리에 따르면 분할 허용(Partition tolerance)을 유지하면서 일관성·가용성을 동시에 100%는 불가능.

그래서 NoSQL은 \"**잠시 다른 답이 나와도 결국 같아진다**\"는 \"eventual consistency\"를 택한다.

> 💡 ACID와 BASE는 \"옳고 그름\"이 아니라 \"무엇이 더 중요한가\"의 선택이다. 은행 이체는 ACID. SNS 좋아요 카운트는 BASE.

## 8. 실무에서 한 번은 만나게 되는 함정 5가지

1. **\"SELECT는 트랜잭션이 아니다\"** → ✗. 모든 SQL은 트랜잭션 안에서 동작. AutoCommit 모드라도 그렇다.
2. **\"DDL을 트랜잭션에 넣어두면 ROLLBACK 가능\"** → ✗. Oracle에서 DDL은 **자동 COMMIT**. PostgreSQL은 트랜잭션 가능.
3. **\"MySQL은 REPEATABLE READ니 안전\"** → △. Phantom Read는 차단되지만 Lost Update는 여전히 가능. `SELECT ... FOR UPDATE` 필요.
4. **\"트랜잭션을 길게 잡으면 정합성에 좋다\"** → ✗. 락 보유 시간이 길어져 데드락·대기·성능 사고.
5. **\"COMMIT 후에도 ROLLBACK 가능\"** → ✗. COMMIT은 \"되돌릴 수 없다\"는 선언.

## 9. 한 줄 요약

> **ACID = \"데이터가 깨지는 4가지 시나리오에 대한 4가지 약속\"**.  
> Atomicity는 *중간 죽음*에, Consistency는 *규칙 위반*에, Isolation은 *동시 충돌*에, Durability는 *물리적 장애*에 대한 답.  
> 락과 MVCC는 Isolation을 구현하는 두 가지 도구이고, 격리 수준은 \"얼마나 엄격하게 막을지\"의 다이얼.
