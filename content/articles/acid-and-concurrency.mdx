> 💡 **이 글에서 답하는 질문**  
> — ACID는 왜 4개일까? 셋이면 안 되나?  
> — Dirty Read, Phantom Read는 왜 \"읽기\" 문제인가? 쓰기가 아니라?  
> — 락(Lock)과 MVCC는 결국 같은 일을 하는 건가, 다른 일을 하는 건가?  
> — SAVEPOINT 후 `ROLLBACK TO sp` 문제를 시험에서 어떻게 한 번에 추적하는가?  
> — REPEATABLE READ인 MySQL InnoDB와 READ COMMITTED인 Oracle은 실무에서 어떤 차이를 만드는가?

\"트랜잭션은 ACID를 보장한다.\" — 이 한 문장은 모든 데이터베이스 책의 첫 페이지에 등장한다. 그런데 ACID라는 네 글자를 외운 사람과, ACID가 무엇을 지키는지 실제로 아는 사람은 다르다. 전자는 \"원자성·일관성·고립성·지속성\"이라고 답하고 끝낸다. 후자는 \"중간에 서버가 죽으면? 두 사용자가 동시에 같은 행을 건드리면? 정전이 나면?\" 같은 시나리오를 머릿속에 그릴 수 있다.

이 글은 1만 원짜리 계좌 이체 한 번을 천천히 따라가면서 ACID의 네 글자가 각각 어떤 사건을 막으려고 만들어졌는지 본다. 그리고 그 중에서도 가장 풍부한 도구를 가진 \"고립성\"이 어떻게 락과 MVCC라는 두 방식으로 구현되는지, 격리 수준 4단계는 사용자에게 어떤 선택을 제공하는지, 시험에서 만나는 SAVEPOINT·격리 수준·락 호환성 문제는 어떻게 단계적으로 추적하는지까지 다룬다.

![육중한 금고의 다이얼과 잠금 장치](https://images.unsplash.com/photo-1554224155-6726b3ff858f?w=1200&q=80&auto=format&fit=crop)
*ACID 네 글자는 \"데이터가 깨지는 네 방향\"에 대한 약속이다. 금고의 다이얼처럼 정교하게 맞물려 작동한다.*

## 1. 평범한 이체 한 번

은행 시스템에서 A씨가 B씨에게 1만 원을 보낸다. 화면에서는 한 번의 클릭이지만, 데이터베이스에서는 두 개의 SQL이 실행된다.

```sql
-- ① A의 잔액에서 1만 원 출금
UPDATE 계좌 SET 잔액 = 잔액 - 10000 WHERE 계좌번호 = 'A';

-- ② B의 잔액에 1만 원 입금
UPDATE 계좌 SET 잔액 = 잔액 + 10000 WHERE 계좌번호 = 'B';
```

A의 처음 잔액이 10만 원, B의 처음 잔액이 5만 원이라 하자. 정상적인 결과는 ①+② 후 A=9만, B=6만, 그리고 시스템 전체의 \"총잔액\"은 15만으로 유지된다.

여기까지는 누구나 안다. 그런데 이 \"단순한\" 두 줄의 SQL은 다음 네 가지 위협 앞에 노출되어 있다.

1. ①은 끝났는데 ② 전에 시스템이 죽으면?
2. 누군가 \"음수 잔액은 안 된다\"는 규칙을 위반하면?
3. 동시에 다른 누군가가 A의 잔액을 건드리면?
4. 모든 게 끝났는데 정전이 나면?

ACID의 네 글자는 이 네 가지 시나리오에 대한 정확히 네 가지 답이다. 임의로 정해진 네 글자가 아니라, **데이터가 깨지는 네 방향에 대한 네 답** 인 것이다.

## 2. 시나리오 ① — 절반만 성공한다면? (원자성, Atomicity)

① 출금까지 끝나서 A의 잔액이 9만으로 저장됐다. 그 직후, ②를 실행하기 직전에 데이터베이스 서버가 죽었다. 정전·하드웨어 고장·OS 패닉·강제 종료, 무엇이든.

다시 켰을 때 상태는 어떨까?

```
A: 10만 - 1만 = 9만 ✓ 저장됨
B: 5만 + 1만 = 6만 ✗ 실행 못 함
```

A의 1만 원은 사라졌고 B는 받지 못했다. **총잔액이 14만으로 줄었다.** 누군가의 돈이 증발했다.

이 비극을 막으려면 두 작업이 \"하나의 단위\"여야 한다는 약속이 필요하다.

> **Atomicity (원자성)**: 트랜잭션 안의 모든 작업이 **다 성공하거나 다 실패**한다. 부분 성공은 없다.

DBMS가 어떻게 이걸 보장하는지를 알아두면, 시험에서 \"원자성의 구현 수단은?\" 같은 문제도 한 번에 답할 수 있다.

### 2-1. UNDO 로그와 REDO 로그

DBMS는 트랜잭션의 모든 변경을 즉시 데이터 파일에 적지 않는다. 대신 다음 두 종류의 로그를 먼저 적는다.

- **UNDO 로그**: \"이 행의 원래 값은 X였다\"는 기록. 트랜잭션이 ROLLBACK되거나 다른 트랜잭션이 \"커밋 전의 옛 값\"을 봐야 할 때 사용.
- **REDO 로그**: \"이 행을 X에서 Y로 바꿀 것이다\"는 기록. 시스템이 죽었을 때 \"적용해야 할 변경\"을 재실행하는 데 사용.

①을 실행하기 전, DBMS는 UNDO 로그에 \"A의 원래 잔액은 10만이었다\"를 적는다. ①을 실행한 후에 시스템이 죽으면, 재시작 시 DBMS가 \"이 트랜잭션은 미커밋이었으니 UNDO 로그를 보고 A를 10만으로 되돌려라\"라고 자기 자신에게 명령한다. **부분 변경이 일어나기 전 상태로 복원**된다.

```
정상 흐름:
1. BEGIN
2. UNDO 로그에 \"A 원래 10만\" 기록
3. UPDATE A (잔액 = 9만)
4. UNDO 로그에 \"B 원래 5만\" 기록
5. UPDATE B (잔액 = 6만)
6. COMMIT → REDO 로그 디스크 강제 기록

시스템이 5번과 6번 사이에서 죽었다면:
재시작 시 → 미커밋 트랜잭션 감지 → UNDO로 A, B를 원상복귀
```

> 📌 시험에서 \"원자성은 어떻게 보장되나?\" → **트랜잭션 로그 (UNDO/REDO)**.  
> SQLD에서 자주 묻는다. 외울 때 \"원자성 = UNDO로 되돌릴 수 있는 능력\"으로 묶어 기억하면 좋다.

### 2-2. 그래서 BEGIN ~ COMMIT의 의미

이 흐름을 알면 \"왜 트랜잭션을 시작했으면 반드시 COMMIT 또는 ROLLBACK\"이라는 말이 나오는지 이해된다. 미결 상태로 두면 UNDO 로그가 정리되지 않고, 변경된 행에 락이 걸려 있고, 데이터 페이지는 메모리에 떠 있는 상태로 \"커밋도 아니고 롤백도 아닌\" 어정쩡한 상태가 된다. 다른 사용자의 트랜잭션이 그 행을 건드리려 하면 무한 대기에 빠진다.

## 3. 시나리오 ② — 음수 잔액이 가능한가? (일관성, Consistency)

A의 잔액이 5천 원인 상태에서 1만 원을 보내려 한다. 출금을 실행하면 잔액은 -5천 원이 된다. 시스템이 이걸 허용하면 안 된다.

여기서 \"일관성\"이 두 가지 층위로 등장한다.

### 3-1. DBMS가 자동으로 막는 무결성

먼저 데이터 무결성의 4가지를 짧게 정리하자.

| 무결성 | 의미 | 구현 |
|---|---|---|
| **개체 무결성 (Entity)** | PK는 NULL/중복 불허용 | PRIMARY KEY 제약 |
| **참조 무결성 (Referential)** | FK는 참조 대상이 존재하거나 NULL | FOREIGN KEY 제약 |
| **도메인 무결성 (Domain)** | 컬럼이 정의된 타입·범위 안의 값 | 데이터 타입 + CHECK 제약 |
| **사용자 정의 무결성** | 업무 규칙 (잔액 ≥ 0 같은) | CHECK 제약, 트리거 |

\"잔액 ≥ 0\"이라는 비즈니스 규칙은 네 번째 \"사용자 정의 무결성\"의 영역이다. CHECK 제약으로 표현 가능.

```sql
ALTER TABLE 계좌 ADD CONSTRAINT chk_잔액 CHECK (잔액 >= 0);
```

이 제약이 걸려 있으면, ①의 UPDATE가 \"잔액 = -5천\"을 시도하는 순간 DBMS가 거부한다. 그 결과 트랜잭션은 자동으로 ROLLBACK되고, A의 잔액은 5천 원 그대로 유지된다.

### 3-2. 일관성의 진짜 의미

> **Consistency (일관성)**: 트랜잭션 **전후**에 데이터가 모든 무결성 제약을 만족하는 상태여야 한다.

여기서 \"전후\"라는 단어가 중요하다. 트랜잭션의 **중간**에는 잠시 일관성이 깨질 수 있다. 예를 들어 ①을 실행하고 ②를 실행하기 전, 시스템 총잔액이 14만이 되는 짧은 순간이 있다. 그러나 트랜잭션이 끝났을 때(COMMIT 또는 ROLLBACK 후)는 반드시 일관성이 회복되어 있어야 한다.

> 📌 시험 함정: \"일관성은 DBMS만의 책임\" → **거짓**.  
> 일관성은 개발자가 제약을 잘 걸어야 한다. \"음수 잔액 금지\"라는 규칙을 CHECK 제약으로 표현하지 않으면, DBMS는 그것을 알지 못한다. 트랜잭션은 \"제약을 지킨 상태에서 다음 상태로 옮겨주는 도구\"일 뿐이다.

### 3-3. 트리거가 하는 일

CHECK 제약으로 표현하기 어려운 복잡한 규칙은 트리거로 처리한다. 예: \"하루 출금 한도가 100만 원\"이라는 규칙.

```sql
CREATE TRIGGER 출금한도검증
BEFORE UPDATE OF 잔액 ON 계좌
FOR EACH ROW
WHEN (NEW.잔액 < OLD.잔액)
BEGIN
  -- 오늘 출금 누적이 100만 초과면 에러
  ...
END;
```

CHECK·제약·트리거 모두 \"일관성을 지키는 도구\"다. 트랜잭션이 일관성을 보장한다는 말은 \"이 도구들을 우회하지 않는다\"는 뜻이다.

## 4. 시나리오 ③ — 두 이체가 동시에? (고립성, Isolation)

ACID의 네 글자 중 가장 풍부한 도구를 가진 것이 고립성이다. 이게 시험에서도 가장 자주 출제되고, 실무에서도 가장 자주 사고가 난다.

A의 잔액이 10만 원이다. 두 트랜잭션 T1, T2가 동시에 \"A에서 7만 원씩 출금\"을 시도한다.

```
시간 →
T1: SELECT 잔액 FROM 계좌 WHERE 계좌번호='A';       -- 10만 읽음
T2:                                                  SELECT 잔액 FROM 계좌 WHERE 계좌번호='A';   -- 10만 읽음
T1: UPDATE 계좌 SET 잔액 = 10만 - 7만 ...;          -- A = 3만
T2:                                                  UPDATE 계좌 SET 잔액 = 10만 - 7만 ...;     -- A = 3만 (덮어씀!)
T1: COMMIT
T2:                                                  COMMIT
```

결과: A=3만. 그러나 두 트랜잭션이 합쳐서 14만을 출금했으니, 정상이라면 A=10만-14만=-4만이어야 한다. **사라진 4만 원의 정체는?** 두 트랜잭션이 같은 출발점(10만)에서 따로 계산했기 때문에, T1의 변경이 T2의 변경에 의해 \"잊혀졌다\". 이 현상을 **Lost Update**라 부른다.

### 4-1. 동시성 사고의 네 가지 유형

Lost Update를 비롯해 동시성 사고는 네 가지로 분류된다. 시험·실무 모두 핵심 출제 포인트.

| 현상 | 무엇이 일어나는가 | 예시 |
|---|---|---|
| **Dirty Read** | T1이 **미커밋** 변경한 값을 T2가 읽음. T1이 ROLLBACK하면 T2는 존재하지 않는 값을 본 셈. | T1: 잔액을 0으로 변경 (미커밋) → T2가 0을 읽음 → T1 ROLLBACK |
| **Lost Update** | 두 트랜잭션이 같은 행을 동시 갱신해 한쪽 변경이 \"잊혀짐\". | 위 시나리오 |
| **Non-repeatable Read** | T1이 같은 행을 두 번 읽었는데 사이에 T2가 갱신해서 값이 다르다. | T1: SELECT A → 10만, T2: UPDATE A → 5만 COMMIT, T1: SELECT A → 5만 |
| **Phantom Read** | T1이 같은 조건의 쿼리를 두 번 실행했는데 사이에 T2가 INSERT해서 행 수가 늘었다. | T1: SELECT COUNT(*) WHERE deptno=10 → 5, T2: INSERT 새 행, T1: 같은 쿼리 → 6 |

이 네 가지를 막기 위해 두 가지 접근이 있다. 락과 MVCC.

### 4-2. 락(Lock) — 비관적 동시성 제어

\"누가 건드릴까봐 미리 막아둔다\"는 발상. 트랜잭션이 어떤 행을 읽거나 쓰기 전에 그 행에 락을 건다. 다른 트랜잭션은 같은 행에 호환되지 않는 락을 걸 수 없어 대기한다.

**락의 종류**:

| 락 | 의미 | 동작 |
|---|---|---|
| **공유락 (S, Shared)** | 읽기용 락 | 읽기 허용, 쓰기 차단. 여러 트랜잭션이 동시에 S를 가질 수 있음. |
| **배타락 (X, Exclusive)** | 쓰기용 락 | 읽기·쓰기 모두 차단. 한 번에 한 트랜잭션만. |
| **의도 락 (IS, IX)** | 계층 표시 | \"이 테이블 안의 어딘가에 S/X락이 있다\"는 표시. 테이블 락과의 충돌 감지에 사용. |

**락 호환성 표**:

|   | S | X |
|---|---|---|
| **S** | 호환 (둘 다 읽기 OK) | 충돌 |
| **X** | 충돌 | 충돌 |

이 표가 SQLD 시험의 단골이다. 핵심은 **\"S끼리는 호환된다\"**. 여러 트랜잭션이 동시에 같은 행을 \"읽기\"만 한다면 서로 막지 않는다. 그러나 누군가가 X락을 가지려 하면 모든 S락이 풀릴 때까지 기다려야 한다.

### 4-3. 데드락 — 락의 어두운 면

락은 강력하지만 위험하다. 두 트랜잭션이 서로의 락을 기다리면 영원히 풀리지 않는 교착 상태가 된다.

```
T1: A 행에 X락 → B 행에 X락 대기
T2: B 행에 X락 → A 행에 X락 대기
   → 둘 다 영원히 대기 (Deadlock)
```

DBMS는 주기적으로 락 대기 그래프를 검사해 사이클이 있으면 \"데드락 감지\". 그 중 한 트랜잭션을 강제 ROLLBACK하고 다른 쪽이 진행하게 한다. 강제 ROLLBACK된 트랜잭션은 클라이언트에 에러를 반환한다.

**데드락 예방**:
- 모든 트랜잭션이 **같은 순서로 락 획득** (예: 항상 작은 ID부터)
- 트랜잭션을 짧게 유지 (락 보유 시간을 줄임)
- 격리 수준을 적정하게 (SERIALIZABLE은 락이 많아 데드락 위험↑)

### 4-4. MVCC — 낙관적 동시성 제어

락의 단점은 명확하다. **읽기와 쓰기가 서로 막는다.** 보고서를 조회하는 SELECT 하나가 1초 걸리는 동안 그 행에 대한 모든 UPDATE가 대기한다. OLTP 시스템에서 이건 큰 문제다.

그래서 또 다른 발상이 등장했다. \"각 트랜잭션은 **자기만의 스냅샷**을 본다.\" 데이터를 직접 잠그지 않고, 행마다 \"버전\"을 두어 트랜잭션이 시작한 시점의 버전을 보여준다.

이 방식을 **MVCC(Multi-Version Concurrency Control)** 라 부른다. Oracle·PostgreSQL·MySQL InnoDB가 기본 채택했고(MySQL InnoDB는 모든 격리 수준에서 MVCC 기반), SQL Server는 \"Read Committed Snapshot Isolation\" 옵션을 켜야 MVCC가 동작한다.

**MVCC의 동작 예**:

```
시간 →
T1 시작 (시점: t0)
T1: SELECT A → 10만 읽음 (스냅샷 t0의 값)
T2 시작 (시점: t1)
T2: UPDATE A = 5만 → COMMIT (새 버전 생성)
T1: SELECT A → 여전히 10만 (T1의 스냅샷은 t0이므로 옛 버전을 봄)
T1: COMMIT
```

T1은 T2의 변경에 영향받지 않는다. 트랜잭션 단위로 \"내가 시작한 시점의 세상\"을 본다. **읽기는 쓰기를 막지 않고, 쓰기는 읽기를 막지 않는다.** 락 없이도 일관성이 유지된다.

물론 마법은 아니다. 옛 버전을 유지하려면 저장 공간이 필요하고, 주기적으로 \"이제 아무도 보지 않는 옛 버전\"을 정리하는 청소 작업(VACUUM 또는 비슷한 메커니즘)이 필요하다.

### 4-5. 락과 MVCC를 함께 쓰기

현대 RDBMS는 보통 둘을 혼용한다.

- **일반 SELECT**: MVCC (락 없이 스냅샷 읽기)
- **갱신용 SELECT**: `SELECT ... FOR UPDATE`로 명시적 X락
- **UPDATE/DELETE**: 자동 X락
- **DDL**: 자동 테이블 락

`SELECT FOR UPDATE`는 \"읽고 나서 곧 갱신할 거니까 지금부터 락을 걸어달라\"는 표현이다. Lost Update를 막는 가장 일반적인 방법.

```sql
BEGIN;
SELECT 잔액 FROM 계좌 WHERE 계좌번호='A' FOR UPDATE;  -- X락
-- 애플리케이션이 잔액을 계산하고
UPDATE 계좌 SET 잔액 = ... WHERE 계좌번호='A';
COMMIT;
```

`FOR UPDATE` 덕분에 다른 트랜잭션이 같은 행에 락을 걸 수 없어, 두 트랜잭션이 순차적으로 진행되게 된다.

### 4-6. 격리 수준 — 사용자가 고르는 다이얼

\"얼마나 엄격하게 막을지\"를 사용자가 SQL 문 또는 세션 설정으로 고를 수 있다. ANSI 표준은 네 단계를 정의한다.

| 격리 수준 | Dirty Read | Non-repeatable Read | Phantom Read | 기본 DBMS |
|---|---|---|---|---|
| **READ UNCOMMITTED** | 발생 | 발생 | 발생 | (거의 안 씀) |
| **READ COMMITTED** | 차단 | 발생 | 발생 | Oracle, PostgreSQL, SQL Server |
| **REPEATABLE READ** | 차단 | 차단 | 발생 | **MySQL InnoDB** |
| **SERIALIZABLE** | 차단 | 차단 | 차단 | (가장 안전·가장 느림) |

높을수록 안전하지만 락이 많아져 성능이 떨어진다. OLTP 시스템 대부분은 READ COMMITTED를 쓴다. MySQL InnoDB만 예외적으로 REPEATABLE READ가 기본인데, 그래서 다른 DBMS에서 마이그레이션할 때 사고가 가끔 나곤 한다.

> 📌 시험에서 \"Dirty Read를 차단하는 최소 수준은?\" → **READ COMMITTED**.  
> \"Phantom Read까지 차단하려면?\" → **SERIALIZABLE**.  
> 외울 때 \"표를 위에서 아래로 한 칸씩 채워간다\"는 식으로 기억하면 좋다.

> **Isolation (고립성)**: 동시에 실행되는 트랜잭션이 **서로 영향을 주지 않는 듯** 동작해야 한다. 단, 얼마나 그렇게 보이게 할지는 격리 수준으로 조절.

## 5. 시나리오 ④ — 정전이 나도 살아남는가? (지속성, Durability)

①+② 둘 다 성공했고 COMMIT까지 끝났다. 그 직후 데이터센터에 정전이 발생한다. 다시 켰을 때 A=9만, B=6만이 그대로 있어야 한다.

문제는 컴퓨터의 작동 방식이다. DBMS는 성능을 위해 데이터를 **메모리(버퍼)** 에 두고 작업하다가, 조건이 맞으면 디스크에 쓴다. COMMIT 시점에 \"실제 데이터 페이지가 디스크에 적혔는지\"는 보장되지 않는다.

그렇다면 COMMIT 직후 정전이 나면 데이터가 날아갈까? 아니다. DBMS는 다음 약속을 한다.

### 5-1. WAL — Write-Ahead Logging

> **WAL의 핵심**: 어떤 변경이든 \"데이터 페이지\"를 디스크에 적기 전에 \"REDO 로그\"를 먼저 디스크에 적는다.

COMMIT 시점에 DBMS가 보장하는 것:
1. **REDO 로그가 디스크에 강제 기록됨** (`fsync` 호출).
2. 실제 데이터 페이지는 메모리에만 있어도 OK.

정전 후 재시작 시:
1. REDO 로그를 읽음.
2. \"커밋된 트랜잭션의 변경\"을 데이터 페이지에 다시 적용 (Roll-forward).
3. \"미커밋 트랜잭션의 변경\"은 UNDO로 되돌림 (Roll-back).

이 과정을 **복구(Recovery)** 라 부른다. WAL 덕분에 \"데이터 페이지를 매번 디스크에 적는 비싼 비용\" 없이도 지속성이 보장된다. 디스크 쓰기 부하가 훨씬 적어진다.

> **Durability (지속성)**: 한 번 COMMIT된 데이터는 **시스템 장애가 나도 영구 보존**.  
> 구현: REDO 로그 + WAL + 백업 + 복제.

### 5-2. 백업과 복제 — 더 큰 재난에 대비

WAL은 디스크 자체가 멀쩡할 때의 이야기다. 디스크가 물리적으로 고장나면? 그래서 추가 보호 장치들이 있다.

- **백업**: 주기적으로 데이터를 별도 저장소에 복사.
- **복제(Replication)**: 같은 데이터를 여러 서버에 동기 유지.
- **HA(High Availability)**: 마스터가 죽으면 자동으로 슬레이브가 승격.

시험 범위는 아니지만, 실무에서 \"지속성\"이라고 말할 때는 보통 이 전체 그림을 가리킨다.

## 6. 시험 빈출 패턴 ① — SAVEPOINT 추적

SQLD에서 가장 자주 출제되는 트랜잭션 문제 유형이 \"SAVEPOINT + ROLLBACK TO\" 시나리오의 최종 상태 추적이다. q-086, q-161 같은 문제들.

### 6-1. 풀이 흐름

```
BEGIN;
INSERT 1;
SAVEPOINT sp1;
INSERT 2;
SAVEPOINT sp2;
INSERT 3;
ROLLBACK TO sp1;
INSERT 4;
COMMIT;
```

한 줄씩 \"현재 임시 상태\"를 적어 가며 추적하면 절대 헷갈리지 않는다.

| 단계 | 명령 | 임시 상태 |
|---|---|---|
| 1 | INSERT 1 | [1] |
| 2 | SAVEPOINT sp1 | [1] (체크포인트 표시) |
| 3 | INSERT 2 | [1, 2] |
| 4 | SAVEPOINT sp2 | [1, 2] (체크포인트 표시) |
| 5 | INSERT 3 | [1, 2, 3] |
| 6 | ROLLBACK TO sp1 | [1] (sp1 시점으로 복귀, 2와 3 모두 취소) |
| 7 | INSERT 4 | [1, 4] |
| 8 | COMMIT | [1, 4] 영구 확정 |

**최종 결과: 1과 4만 존재.**

핵심 규칙 두 가지:
1. `ROLLBACK TO sp`는 그 SAVEPOINT 시점까지만 되돌린다. 전체 ROLLBACK이 아니다.
2. 한 SAVEPOINT로 되돌리면, 그 이후 만들어진 다른 SAVEPOINT는 모두 사라진다 (위 예에서 sp2도 함께 무효화).

### 6-2. 자주 만나는 함정

**함정**: \"ROLLBACK TO sp1 후 sp2로 다시 ROLLBACK TO 가능\" → **거짓**. sp1으로 되돌리는 순간 sp2는 무효화되어 더 이상 참조할 수 없다.

**함정**: \"ROLLBACK TO 후 자동으로 COMMIT\" → **거짓**. ROLLBACK TO는 단순히 \"부분 취소\"이고, 트랜잭션은 여전히 진행 중. 이후에 별도로 COMMIT 또는 ROLLBACK이 필요.

## 7. 시험 빈출 패턴 ② — 격리 수준과 현상

\"Dirty Read를 차단하는 최소 격리 수준은?\" → READ COMMITTED.  
\"Phantom Read까지 차단하려면?\" → SERIALIZABLE.  
\"MySQL InnoDB의 기본 격리 수준은?\" → REPEATABLE READ.

이 세 가지 패턴이 거의 매 회 출제된다. 표를 외워두면 풀이가 1초.

```
READ UNCOMMITTED   ← 모두 발생
READ COMMITTED     ← Dirty만 차단    (Oracle 기본)
REPEATABLE READ    ← Phantom만 발생  (MySQL 기본)
SERIALIZABLE       ← 모두 차단
```

추가 함정:
- \"REPEATABLE READ가 가장 안전\" → **거짓**. SERIALIZABLE이 가장 안전.
- \"READ COMMITTED는 Phantom Read를 차단\" → **거짓**. Phantom은 SERIALIZABLE만 차단.

## 8. 시험 빈출 패턴 ③ — DDL과 자동 커밋

\"트랜잭션 안에서 DDL을 실행하면 ROLLBACK 가능한가?\" 라는 질문.

Oracle의 답: **불가능**. DDL은 자동 COMMIT이며, 직전 DML 변경사항까지 함께 커밋된다.

```sql
BEGIN;
UPDATE emp SET sal = 0;   -- 미커밋 DML
CREATE TABLE backup AS SELECT * FROM emp;   -- DDL → 자동 COMMIT
ROLLBACK;   -- 효과 없음! UPDATE도 이미 커밋됨
```

이 동작은 Oracle 특유의 것이다. PostgreSQL은 DDL도 트랜잭션 안에 넣어 ROLLBACK 가능하게 한다. SQLD는 Oracle 기준이므로 \"DDL = 자동 COMMIT\"으로 외워두면 된다.

## 9. NoSQL의 \"BASE\"는 무엇인가

종종 \"NoSQL은 ACID 대신 BASE\"라는 말을 듣는다. BASE는 다음 세 글자의 약어다.

- **B**asically Available: 기본적으로 가용
- **S**oft State: 시스템 상태가 시간에 따라 변할 수 있음
- **E**ventually Consistent: 결국 일관성에 도달

핵심은 \"분산\"이다. 데이터가 수십~수백 대 서버에 흩어져 있을 때, \"모든 서버가 즉시 같은 값을 보여주는 일관성\"은 매우 비싸다. **CAP 정리**에 따르면 분산 시스템에서 Consistency·Availability·Partition tolerance 중 두 가지만 만족할 수 있다(셋 다는 불가능).

ACID는 C(일관성)와 A(가용성, 적어도 같은 노드 내에서)에 집중하고, BASE는 P(분할 허용)와 A에 집중한다. \"잠시 다른 값이 보여도 결국 같아진다\"는 약속.

은행 이체는 ACID. SNS 좋아요 카운트는 BASE. 어느 한쪽이 옳은 게 아니라 **무엇이 더 중요한가의 선택**이다.

## 10. 실무에서 자주 만나는 함정 7가지

1. **\"SELECT는 트랜잭션이 아니다\"** → 거짓. 모든 SQL은 트랜잭션 안에서 동작.
2. **\"AutoCommit 모드면 트랜잭션이 없는 것\"** → 거짓. 매 SQL이 자동으로 BEGIN/COMMIT되는 것일 뿐.
3. **\"DDL을 트랜잭션에 넣으면 ROLLBACK 가능\"** → Oracle에서는 거짓. PostgreSQL은 가능.
4. **\"MySQL의 REPEATABLE READ가 모든 동시성 문제를 막아준다\"** → 거짓. Phantom은 막지만 Lost Update는 여전히 가능. `FOR UPDATE` 필요.
5. **\"트랜잭션을 길게 잡으면 안전해진다\"** → 거짓. 락 보유 시간이 길어져 데드락·대기·성능 사고가 늘어난다.
6. **\"COMMIT 후에도 ROLLBACK 가능\"** → 거짓. COMMIT은 되돌릴 수 없다.
7. **\"공유락끼리는 충돌한다\"** → 거짓. 공유락끼리는 호환된다. 호환되지 않는 건 S↔X와 X↔X.

## 11. 마치며 — 네 글자가 지키는 것

ACID라는 네 글자는 외워야 할 단어가 아니다. 그것은 \"데이터가 깨지는 네 가지 방향\"에 대한 답이며, 각각의 글자 뒤에는 1만 원짜리 이체 한 번에 숨어 있던 구체적인 시나리오가 있다. 중간에 시스템이 죽으면 돈이 사라지고, 규칙이 깨지면 음수 잔액이 생기고, 둘이 동시에 건드리면 한쪽 변경이 잊혀지고, 정전이 나면 커밋된 거래가 증발한다. 데이터베이스가 이 네 가지를 모두 막아주기 때문에 우리는 은행 잔액을 신뢰하고, 항공권 좌석을 두 번 팔지 않는 시스템을 만들 수 있다.

흥미로운 점은 이 네 가지가 서로 다른 도구로 구현된다는 사실이다. 원자성은 트랜잭션 로그(UNDO)로, 일관성은 제약조건과 트리거로, 고립성은 락과 MVCC와 격리 수준으로, 지속성은 REDO 로그와 WAL로 지켜진다. 그 중에서도 가장 풍부한 도구를 가진 것이 고립성이다. 락은 \"누가 건드릴까봐 미리 막아두는\" 비관적 접근이고, MVCC는 \"각자 자기 스냅샷을 본다\"는 낙관적 접근이다. 두 방식은 서로 다른 트레이드오프를 가지며, 현대의 RDBMS는 대부분 두 가지를 혼용한다. 그리고 격리 수준이라는 다이얼은 \"얼마나 엄격하게 막을지\"를 사용자가 선택할 수 있게 해준다. 안전과 성능 사이의 균형은 결국 시스템마다 다르고, 그 선택을 사용자의 손에 맡긴 것이 SQL 표준의 깊이다.

ACID와 BASE 사이의 논쟁도 결국 같은 균형의 문제다. 은행 이체에는 ACID가 필요하고, SNS 좋아요 카운트에는 BASE가 어울린다. 어느 한쪽이 옳은 것이 아니라, 무엇을 더 중요하게 여기느냐의 선택일 뿐이다. RDBMS는 ACID를 기본값으로 두기 때문에 우리가 데이터의 \"무결성\"에 대해 거의 의식하지 않고 코드를 쓸 수 있다. 이 보이지 않는 보호가 얼마나 정교한 약속들 위에 서 있는지를 알게 되면, 단순한 `COMMIT` 한 줄이 이전과 다르게 보인다.

시험장에서 트랜잭션 문제를 만나면, 외운 정의를 떠올리기 전에 \"이게 어떤 시나리오를 막는 거지?\" 라고 먼저 물어보자. 원자성은 \"중간 죽음\"을, 일관성은 \"규칙 위반\"을, 고립성은 \"동시 충돌\"을, 지속성은 \"물리적 장애\"를 막는다. 이 네 가지 시나리오를 머릿속에 그릴 수 있다면 거의 모든 트랜잭션 문제가 다음 한 줄로 정리된다. \"이 시나리오를 막는 게 ACID 중 어느 글자인가\".

다음 편에서는 데이터를 \"분석\"하는 새로운 언어 — GROUP BY가 풀지 못하고 윈도우 함수만 풀 수 있는 문제들 — 의 직관을 따라간다.
