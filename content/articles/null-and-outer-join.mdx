> 💡 **이 글에서 답하는 질문**  
> — 왜 `WHERE comm = NULL`이 안 되고 `IS NULL`을 써야 할까?  
> — 왜 `NOT IN (10, 20, NULL)`은 결과가 항상 비는가?  
> — LEFT OUTER JOIN을 했는데 WHERE 조건을 추가하니 결과가 INNER JOIN과 같아지는 이유는?  
> — Oracle의 `(+)` 위치를 어떻게 외우면 안 헷갈리는가?  
> — DECODE의 \"NULL = NULL은 TRUE\"라는 특수 동작은 시험에 어떻게 나오는가?

NULL은 SQL에서 가장 작은 단어이지만 가장 많은 사고를 일으킨다. 실무에서 만나는 데이터 사고의 절반쯤은 어딘가에서 NULL이 끼어들어 \"이럴 줄 몰랐다\"는 결과를 만드는 데서 시작한다. 시험에서도 NULL 관련 문제는 거의 매 회 출제되며, 정규화와 함께 가장 자주 나오는 \"함정의 모음\"이기도 하다.

이 글은 NULL이 왜 그런 식으로 동작하는지를 \"3치 논리\"라는 단 하나의 개념에서 출발해 따라간다. 그리고 그 한 줄의 개념이 어떻게 NOT IN·OUTER JOIN·집계 함수·정렬·DECODE라는 다섯 가지 영역에서 모든 함정을 만들어내는지를 본다. 마지막에는 시험에 자주 나오는 NULL 관련 문제의 풀이 흐름을 정리한다.

## 1. NULL은 \"없음\"이 아니다

처음 SQL을 배우는 사람의 대부분이 NULL을 \"빈 값\"이나 \"0\"으로 오해한다. 사실은 다르다.

> **NULL의 정의**: 이 값이 무엇인지 **알 수 없다(Unknown)**.

이 작은 차이가 모든 함정의 시작이다. 다음 두 경우는 의미가 완전히 다르다.

- `comm = 0` : 커미션이 \"0원\"이라고 **확정**되어 있다.
- `comm = NULL` : 커미션이 얼마인지 \"**모른다**\".

전자는 \"받지 못함이 확실\"이고, 후자는 \"받았는지 못 받았는지 미정\"이다. 회계 시스템에서 두 의미는 명확히 구분되어야 한다.

NULL은 \"빈 문자열\"과도 다르다. `''`(빈 문자열)은 \"길이 0의 문자열이 존재\"라는 의미이고, `NULL`은 \"문자열이 무엇인지 모름\"이다. 이 미세한 차이를 의식하지 못하면 데이터의 의미가 흐려진다.

> 💡 SQL이 NULL이라는 별도 상태를 정의한 이유는, 현실의 데이터에 \"미정\" 상태가 너무 많기 때문이다. 신입 사원의 부서는 입사 직후 미정일 수 있고, 신상품의 단가는 출시 전 미정일 수 있다. 이런 \"진짜 모름\"을 0이나 빈 문자열로 메우면 의미가 왜곡된다. NULL은 \"모름\"을 정직하게 표현하는 가장 좋은 도구다.

## 2. 3치 논리 — SQL은 거짓말을 하지 않는다

대부분의 프로그래밍 언어는 **2치 논리**(TRUE / FALSE)로 동작한다. 그러나 SQL은 **3치 논리**(TRUE / FALSE / **UNKNOWN**)다.

```sql
NULL = NULL       -- UNKNOWN
NULL = 100        -- UNKNOWN
NULL <> 100       -- UNKNOWN
NULL > 0          -- UNKNOWN
NULL = ''         -- UNKNOWN  (Oracle 제외, Oracle은 빈 문자열을 NULL로 봄)
```

\"모름과 모름이 같은가?\" 라는 질문에 가장 정직한 답은 \"모른다\"이다. SQL은 거짓말을 하지 않는다. 두 값이 모두 NULL이라는 사실은 그 둘이 같다는 의미가 아니라, 둘 다 무엇인지 모른다는 의미일 뿐이다.

문제는 **WHERE 절은 TRUE인 행만 통과**시킨다는 점이다. UNKNOWN은 통과 못 한다.

```sql
WHERE comm = NULL
-- comm의 값이 무엇이든 \"NULL과의 비교\"는 항상 UNKNOWN
-- → 모든 행이 탈락
-- → 결과 0건
```

그래서 \"NULL인 행을 찾아라\"는 별도 연산자가 필요하다.

```sql
WHERE comm IS NULL       -- ✓
WHERE comm IS NOT NULL   -- ✓
```

`IS NULL`은 SQL이 NULL을 다루기 위해 특별히 만들어둔 \"유일한 합법적 비교\"다. 이걸 모르면 NULL을 가진 행을 절대 못 찾는다.

### 2-1. AND, OR의 3치 진리표

3치 논리에서 AND와 OR이 어떻게 동작하는지를 외워두면 NULL 관련 사고의 80%를 막을 수 있다.

| AND | TRUE | FALSE | UNKNOWN |
|---|---|---|---|
| TRUE | TRUE | FALSE | UNKNOWN |
| FALSE | FALSE | FALSE | FALSE |
| UNKNOWN | UNKNOWN | FALSE | UNKNOWN |

| OR | TRUE | FALSE | UNKNOWN |
|---|---|---|---|
| TRUE | TRUE | TRUE | TRUE |
| FALSE | TRUE | FALSE | UNKNOWN |
| UNKNOWN | TRUE | UNKNOWN | UNKNOWN |

핵심 두 가지:
- **`FALSE AND ?` = FALSE** (?가 무엇이든)
- **`TRUE OR ?` = TRUE** (?가 무엇이든)

이 두 가지가 SQL이 \"단락 평가(short-circuit)\"를 안전하게 할 수 있게 해준다. 그러나 그 외의 모든 경우에 UNKNOWN이 등장하면, UNKNOWN이 전파된다. 거의 모든 NULL 사고가 이 진리표 한 줄에서 시작된다.

## 3. NULL과 산술 연산

```sql
NULL + 100   -- NULL
NULL * 0     -- NULL
NULL / 1     -- NULL
```

규칙: **한쪽이 NULL이면 결과도 NULL** (NULL 전파).

\"NULL × 0이 0이어야 하지 않나?\" 라고 묻는 사람이 있다. 수학적으로는 \"0을 곱하면 0\"이 맞지만, SQL의 관점에서 \"모르는 수에 0을 곱하면 결과는 정말로 0이 보장되는가?\" 라는 질문이 된다. 만약 \"모르는 수\"가 사실은 NaN이거나 정의되지 않은 값이라면? SQL은 일관성을 위해 \"모르는 것과의 연산은 모름\"을 유지한다.

### 3-1. 문자열 연결의 예외

```sql
NULL || 'A'   -- 'A'      (Oracle)
CONCAT(NULL, 'A')   -- 'A' (DBMS마다 다름; SQL Server는 NULL)
```

Oracle은 \"||\" 연산자에서 NULL을 빈 문자열처럼 다룬다. 이건 Oracle의 특이한 동작이다. 다른 DBMS는 표준대로 NULL이 전파된다(MySQL의 CONCAT은 예외적으로 NULL을 무시하는 옵션 있음). 이런 미세한 차이가 마이그레이션 시 사고를 만든다.

## 4. 집계 함수는 NULL을 \"건너뛴다\"

이 부분이 묘하게 일관성이 깨지는 지점이다. WHERE는 NULL을 \"UNKNOWN\"으로 다뤄 탈락시키지만, 집계 함수는 NULL을 \"무시\"하고 결과를 만든다.

```sql
-- sal: 1000, 2000, NULL, 3000
SELECT COUNT(*), COUNT(sal), SUM(sal), AVG(sal) FROM emp;
```

| 함수 | 결과 | 설명 |
|---|---|---|
| `COUNT(*)` | **4** | 전체 행 (NULL 행 포함) |
| `COUNT(sal)` | **3** | NULL이 아닌 행만 |
| `SUM(sal)` | **6000** | NULL 제외하고 합산 (1000+2000+3000) |
| `AVG(sal)` | **2000** | 6000 / 3 (NULL 제외 평균) ← 6000/4가 아님! |

여기서 가장 자주 사고가 나는 함정 두 개.

**함정 1**: AVG는 6000/4가 아니라 6000/3이다. NULL을 평균 분모에 포함하지 않는다. 의미상 \"평균 sal\"이라고 하면 자연스러운 결과이지만, \"NULL을 0으로 보고 평균을 내야 하는 경우\"를 만나면 명시적으로 `AVG(NVL(sal, 0))`을 써야 한다.

**함정 2**: 모든 값이 NULL인 컬럼의 `SUM`은 0이 아니라 **NULL**이다.

```sql
-- sal: NULL, NULL, NULL
SELECT SUM(sal) FROM emp;   -- NULL (0이 아님!)
```

이건 의외다. \"합이 0이어야 한다\"고 기대하는 사람이 많지만, NULL을 무시하고 남은 게 0개이므로 \"합이 정의되지 않음\" = NULL이다. 0이 필요하면 `COALESCE(SUM(sal), 0)`을 써야 한다.

### 4-1. GROUP BY의 NULL 처리

```sql
SELECT deptno, COUNT(*) FROM emp GROUP BY deptno;
```

deptno가 (10, 10, 20, NULL, NULL)이면 GROUP BY는 다음과 같이 묶는다.

| deptno | COUNT(*) |
|---|---|
| 10 | 2 |
| 20 | 1 |
| NULL | 2 |

**GROUP BY는 NULL을 \"하나의 그룹\"으로 모은다.** WHERE 절에서는 NULL이 UNKNOWN으로 탈락되지만, GROUP BY는 \"NULL = NULL을 같은 그룹으로\" 본다. 이 미세한 일관성 깨짐이 사고를 만든다.

> 📌 시험에서 \"GROUP BY는 NULL을 결과에서 제외한다\" → **거짓**. NULL을 하나의 그룹으로 포함한다.

## 5. NOT IN의 함정 — 가장 유명한 사고

NULL 관련 시험·실무 문제 1순위가 이것이다.

```sql
-- dept 테이블에 deptno = NULL인 행이 하나라도 있다고 하자
SELECT * FROM emp
WHERE deptno NOT IN (SELECT deptno FROM dept);
```

직관적으로 보면 \"부서에 존재하지 않는 부서번호를 가진 사원\"을 가져올 것 같다. 그러나 실제 결과는 **항상 빈 결과**다.

### 5-1. 왜 그런가

`NOT IN (10, 20, NULL)`은 다음과 같이 풀린다.

```
deptno <> 10 AND deptno <> 20 AND deptno <> NULL
                                  ^^^^^^^^^^^^^^^^
                                  UNKNOWN
```

마지막 항이 UNKNOWN이다. 그리고 위에서 본 진리표에 따라 `TRUE AND TRUE AND UNKNOWN` = UNKNOWN, `FALSE AND _ AND _` = FALSE. 어떤 경우든 결과가 **TRUE가 되지 못한다**. WHERE는 TRUE만 통과시키므로 모든 행이 탈락.

### 5-2. 해결책 세 가지

**방법 1: 서브쿼리에서 NULL을 제거**

```sql
WHERE deptno NOT IN (SELECT deptno FROM dept WHERE deptno IS NOT NULL)
```

가장 직관적인 해결책. 다만 \"부서 테이블에 NULL이 절대 없다고 보장\"되지 않으면 매번 IS NOT NULL을 추가하는 게 안전.

**방법 2: NOT EXISTS 사용**

```sql
WHERE NOT EXISTS (
  SELECT 1 FROM dept d WHERE d.deptno = e.deptno
)
```

EXISTS는 \"매칭되는 행이 있는가\"를 묻는다. NULL은 매칭에 참여하지 못하므로(`NULL = NULL`이 UNKNOWN이라) 자동으로 처리된다.

**방법 3: LEFT OUTER JOIN + IS NULL**

```sql
SELECT e.*
FROM emp e
LEFT OUTER JOIN dept d ON e.deptno = d.deptno
WHERE d.deptno IS NULL
```

\"부서와 매칭되지 않은 사원\"을 찾는 표현. 옵티마이저가 이걸 가장 잘 최적화하는 경우가 많아 대규모 데이터에서 성능적으로도 유리하다.

> 📌 시험에서 \"NOT IN 서브쿼리에 NULL이 섞이면 어떤 결과가?\" → **항상 빈 결과**. 가장 자주 나오는 SQL 함정 문제.

## 6. OUTER JOIN — NULL을 \"만들어내는\" 도구

INNER JOIN은 양쪽에 매칭되는 행만 결과에 넣는다. OUTER JOIN은 그 반대 — 매칭되지 않는 쪽도 결과에 포함시키고, 빈 자리는 **NULL로 채운다.**

```
emp: (1, 10), (2, 20), (3, NULL)
dept: (10, 'A'), (30, 'C')

SELECT * FROM emp e LEFT OUTER JOIN dept d ON e.deptno = d.deptno;
```

| emp.empno | emp.deptno | dept.deptno | dept.dname |
|---|---|---|---|
| 1 | 10 | 10 | A |
| 2 | 20 | NULL | NULL | ← deptno=20인 부서 없음 → NULL로 채움
| 3 | NULL | NULL | NULL | ← emp.deptno=NULL → 어떤 부서와도 매칭 안 됨 → NULL로 채움

여기서 \"emp.deptno=NULL\"인 사원도 결과에 들어왔다. NULL이 어떤 값과도 매칭되지 않아서 dept.deptno는 NULL로 채워졌지만, LEFT OUTER JOIN 규칙이 \"왼쪽 전체 보존\"이므로 사원 행 자체는 살아남는다.

### 6-1. LEFT/RIGHT/FULL OUTER JOIN의 차이

| 종류 | 의미 |
|---|---|
| **INNER JOIN** | 양쪽 매칭만 |
| **LEFT OUTER JOIN** | 왼쪽 전체 + 매칭 (오른쪽 없으면 NULL) |
| **RIGHT OUTER JOIN** | 오른쪽 전체 + 매칭 (왼쪽 없으면 NULL) |
| **FULL OUTER JOIN** | 양쪽 모두 (안 매칭은 NULL) |

### 6-2. FULL OUTER JOIN의 행 수 공식

`len(FULL OUTER) = len(A) + len(B) - 매칭_수`

```
A = {1, 2, 3}, B = {2, 3, 4}, 매칭 = 2건
FULL OUTER 결과: 3 + 3 - 2 = 4행
```

시험에서 \"결과 행 수\"를 묻는 문제는 이 공식 하나면 끝.

## 7. LEFT OUTER JOIN + WHERE의 가장 흔한 사고

이게 OUTER JOIN에서 가장 자주 일어나는 실수다. 시험에서도 거의 매 회 출제된다.

```sql
-- 의도: \"모든 사원, 그리고 만약 부서가 있다면 서울 부서인 사람만\"
SELECT e.ename, d.loc
FROM emp e LEFT OUTER JOIN dept d ON e.deptno = d.deptno
WHERE d.loc = 'SEOUL';
```

뭐가 잘못됐을까? 결과는 의도와 달리 \"서울 부서에 속한 사원만\" 나온다. 부서가 없는 사원은 사라졌다. **사실상 INNER JOIN과 같은 결과**가 된 것이다.

### 7-1. 왜 그런가

WHERE는 ON보다 나중에 평가된다.

흐름:
1. **`LEFT OUTER JOIN ON ...`**: 모든 사원 + 매칭된 부서를 만든다. 매칭 없는 사원은 dept 컬럼이 NULL.
2. **`WHERE d.loc = 'SEOUL'`**: NULL과 'SEOUL'의 비교는 UNKNOWN → 모든 NULL 행이 탈락.

결과적으로 \"부서가 있는 사원 중에서 서울 부서인 사람만\" 남는다. LEFT OUTER가 무력화된다.

### 7-2. 해결: 조건을 ON으로 옮기기

```sql
-- ✓ 의도대로 동작
SELECT e.ename, d.loc
FROM emp e LEFT OUTER JOIN dept d
  ON e.deptno = d.deptno AND d.loc = 'SEOUL';
```

이렇게 하면:
- 조인 단계에서 `d.loc = 'SEOUL'`인 부서만 매칭한다.
- 매칭되지 않은 사원은 `d.loc`이 NULL인 채로 결과에 남는다.
- 모든 사원이 살아남는다.

> 💡 **외워둘 규칙**: OUTER JOIN에서 \"오른쪽(없을 수 있는 쪽)\"의 컬럼에 조건을 걸 거면, 그 조건은 **반드시 ON에**. WHERE에 넣으면 외부 조인이 내부 조인으로 변질된다.

이 규칙은 거꾸로도 성립한다. \"왼쪽\" 조건은 WHERE에 둬도 안전하다 (왼쪽은 어차피 보존되므로 NULL이 되지 않는다).

```sql
-- ✓ 안전 (e.deptno는 OUTER JOIN으로 NULL이 되지 않음)
SELECT e.ename, d.loc
FROM emp e LEFT OUTER JOIN dept d ON e.deptno = d.deptno
WHERE e.hiredate >= '2020-01-01';
```

### 7-3. 자주 만나는 시험 함정

- 의도가 \"왼쪽 전체 + 조건 매칭\"인데 WHERE에 오른쪽 조건 → INNER JOIN으로 변질
- 해결: 조건을 ON 절에 넣기
- 반대로 \"왼쪽 조건 + 오른쪽 매칭\"이면 WHERE에 왼쪽 조건이 자연스럽다

## 8. Oracle (+)의 위치 함정

Oracle은 ANSI 표준이 등장하기 전부터 자체 외부 조인 표기를 썼다.

```sql
SELECT * FROM emp e, dept d
WHERE e.deptno = d.deptno(+);
```

`(+)`의 위치를 외우는 가장 쉬운 방법은 \"**NULL을 채울 쪽에 (+)를 붙인다**\".

`d.deptno(+)` → d 쪽이 NULL이 될 수 있음 → e가 기준 → **LEFT OUTER JOIN (왼쪽 = emp)**.

| Oracle 구문 | ANSI 동치 |
|---|---|
| `WHERE A.x = B.y(+)` | `A LEFT OUTER JOIN B ON A.x = B.y` |
| `WHERE A.x(+) = B.y` | `A RIGHT OUTER JOIN B ON A.x = B.y` |
| 양쪽 `(+)` 동시에 | **불가능** (FULL OUTER는 ANSI로만) |

### 8-1. (+)가 실무에서 권장되지 않는 이유

- 가독성이 떨어짐 (특히 여러 테이블 조인 시)
- FULL OUTER JOIN이 불가능
- 옵티마이저가 잘못 해석하는 케이스가 가끔 있음
- 다른 DBMS와의 호환성 없음

그래도 SQLD 시험에는 자주 나오므로 \"(+) 위치 → NULL 채울 반대편\" 정도는 외워두자.

## 9. 정렬 시 NULL의 위치 — DBMS마다 다른 동작

```sql
SELECT * FROM emp ORDER BY comm;
```

NULL은 어디로 갈까? **DBMS마다 다르다.**

| DBMS | ASC 기본 | DESC 기본 |
|---|---|---|
| **Oracle** | NULL이 **마지막** | NULL이 **처음** |
| **PostgreSQL** | NULL이 마지막 | NULL이 처음 |
| **MySQL** | NULL이 **처음** | NULL이 마지막 |
| **SQL Server** | NULL이 처음 | NULL이 마지막 |

명시적으로 지정하려면:

```sql
ORDER BY comm ASC NULLS LAST     -- Oracle, PostgreSQL
ORDER BY comm DESC NULLS FIRST
```

(MySQL은 NULLS FIRST/LAST 키워드를 지원하지 않고 IS NULL과 함께 정렬해야 함)

> 📌 시험에서 \"Oracle ORDER BY ASC에서 NULL은 어디?\" → **마지막**. SQLD는 Oracle 기준이므로 위 표 첫 줄을 외워두자.

## 10. NULL 함수 카탈로그

NULL을 다루는 주요 함수들이다. 시험에서 자주 등장하므로 표를 외워두면 좋다.

| 함수 | 동작 | 호환성 |
|---|---|---|
| `NVL(a, b)` | a가 NULL이면 b, 아니면 a | Oracle |
| `NVL2(a, b, c)` | a가 NOT NULL이면 b, NULL이면 c | Oracle |
| `COALESCE(a, b, c, ...)` | 첫 번째 NOT NULL 값 | **ANSI 표준** |
| `NULLIF(a, b)` | a = b면 NULL, 아니면 a | ANSI 표준 |
| `IS NULL` / `IS NOT NULL` | NULL 여부 확인 | ANSI 표준 |

\"NVL\"은 Oracle 방언이고 \"COALESCE\"는 표준이다. 호환성을 위해 COALESCE를 권장하지만, Oracle 환경에서는 NVL도 자주 본다.

```sql
SELECT
  NVL(comm, 0),                     -- comm이 NULL이면 0
  COALESCE(phone1, phone2, '없음'),  -- 첫 NOT NULL
  NULLIF(status, 'N/A')             -- 'N/A'면 NULL로 변환
FROM emp;
```

### 10-1. 함수 결과 함정 (q-054, q-118)

```sql
SELECT NVL(NULL, 'A') FROM dual;            -- 'A'
SELECT COALESCE(NULL, NULL, 'A') FROM dual; -- 'A'
SELECT NVL2(NULL, 'B', 'A') FROM dual;      -- 'A' (NULL일 때 3번째 인자)
SELECT NULLIF('A', 'A') FROM dual;          -- NULL (같으면 NULL)
```

이 네 함수의 결과가 시험에서 자주 비교 출제된다. 외울 때 \"NVL은 NULL을 다른 값으로 대체, NULLIF는 같은 값을 NULL로 변환\"이라는 반대 의미로 묶어 기억하자.

## 11. DECODE의 특수 동작 — NULL = NULL이 TRUE?

Oracle의 `DECODE` 함수는 SQL의 일반 원칙을 깬다. NULL = NULL을 **TRUE로 처리**하는 유일한 케이스다.

```sql
SELECT DECODE(NULL, NULL, '같음', '다름') FROM dual;
-- 결과: '같음'  ← NULL = NULL을 TRUE로 봄
```

같은 의도를 CASE로 쓰면 다른 결과가 나온다.

```sql
SELECT CASE WHEN NULL = NULL THEN '같음' ELSE '다름' END FROM dual;
-- 결과: '다름'  ← NULL = NULL은 UNKNOWN → ELSE로
```

이 차이가 시험에 자주 출제된다(q-120). \"DECODE는 NULL을 어떻게 처리하는가\" → \"NULL = NULL을 TRUE로 처리\".

CASE로 같은 효과를 내려면 명시적으로:

```sql
CASE WHEN NULL IS NULL THEN '같음' ELSE '다름' END   -- '같음'
```

DECODE는 등치(=) 비교만 가능한 함수이고 Oracle 전용이지만, NULL 비교의 특수 동작 때문에 자주 사용된다.

## 12. 시험 빈출 패턴 모음

### 12-1. 패턴 A: COUNT와 NULL (q-012, q-111)

```sql
-- sal: 1000, 2000, NULL, 3000
SELECT COUNT(*), COUNT(sal), COUNT(DISTINCT sal) FROM emp;
-- → 4, 3, 3   (DISTINCT는 NULL 제외)
```

### 12-2. 패턴 B: IN with NULL (q-045)

```sql
WHERE sal IN (1000, 2000, NULL)
-- sal이 NULL인 행은 매칭 안 됨 (NULL = NULL은 UNKNOWN)
```

### 12-3. 패턴 C: NOT IN with NULL (q-066, q-138)

```sql
WHERE sal NOT IN (1000, 2000, NULL)
-- 항상 빈 결과
```

### 12-4. 패턴 D: WHERE + NULL 비교 (q-112)

```sql
WHERE comm = NULL    -- ✗ 결과 0건
WHERE comm IS NULL   -- ✓ 정상
```

### 12-5. 패턴 E: LEFT OUTER + WHERE 함정 (q-122)

```sql
-- 의도와 다른 결과
FROM emp e LEFT JOIN dept d ON e.deptno = d.deptno
WHERE d.loc = 'SEOUL'   -- 사실상 INNER JOIN
```

### 12-6. 패턴 F: Oracle (+) → ANSI 변환 (q-049, q-123)

```sql
WHERE A.x = B.y(+)   →   A LEFT OUTER JOIN B ON A.x = B.y
WHERE A.x(+) = B.y   →   A RIGHT OUTER JOIN B ON A.x = B.y
```

### 12-7. 패턴 G: NVL/COALESCE/NULLIF/DECODE 결과 비교 (q-054, q-118, q-120)

각 함수의 결과를 표로 외워두자.

## 13. NULL 사용의 실무 원칙

**NULL을 의미적으로 구분해서 쓰자.**

- 미정/모름 → NULL이 적합
- \"빈 문자열\"이나 \"0\"의 의미가 명확하면 → NULL 대신 명시적 값
- FK의 \"선택 관계\" → NULL 허용 (선택성)

**제약 조건으로 NULL을 통제하자.**

- PK는 자동 NOT NULL
- 필수 컬럼은 명시적 NOT NULL
- UNIQUE는 NULL을 여러 개 허용 (Oracle, ANSI 기본)

**조회 SQL에서는 NULL을 항상 \"세 번째 가능성\"으로 두고 생각하자.**

- \"이 조건이 NULL을 만나면 어떻게 평가될까?\"
- WHERE는 TRUE만 통과 → NULL은 자동 탈락
- COUNT, SUM, AVG는 NULL을 무시 → 의도 확인
- GROUP BY는 NULL을 하나의 그룹으로 묶음
- ORDER BY는 DBMS마다 NULL 위치가 다름

## 14. 자주 만나는 함정 정리

1. **\"NULL은 0과 같다\"** → 거짓. NULL은 \"모름\", 0은 \"0\"이라고 확정된 값.
2. **\"NULL = NULL은 TRUE\"** → 거짓. UNKNOWN. (단 DECODE만 예외)
3. **\"NOT IN 서브쿼리는 NULL이 있어도 정상 동작\"** → 거짓. 항상 빈 결과.
4. **\"AVG는 NULL을 0으로 보고 평균을 낸다\"** → 거짓. NULL을 제외하고 평균.
5. **\"GROUP BY는 NULL을 결과에서 제외\"** → 거짓. NULL을 하나의 그룹으로 포함.
6. **\"LEFT OUTER JOIN의 WHERE 조건은 OUTER JOIN을 유지\"** → 거짓. 오른쪽 컬럼 조건을 WHERE에 두면 INNER로 변질.
7. **\"Oracle ORDER BY ASC는 NULL이 처음\"** → 거짓. **마지막**.
8. **\"UNIQUE는 NULL을 허용 안 함\"** → 거짓. NULL은 여러 개 허용 가능.

## 15. 마치며 — 가장 작은 단어, 가장 큰 함정

NULL이라는 네 글자가 일으키는 사고의 양은 그 글자 수에 비례하지 않는다. 실무에서 만나는 데이터 사고의 절반쯤은 어딘가에서 NULL이 끼어들어 \"이럴 줄 몰랐다\"는 결과를 만드는 데서 시작한다. 이상한 점은 SQL이 결코 거짓말을 하지 않는다는 사실이다. NULL은 \"값이 없다\"가 아니라 \"값을 알 수 없다\"는 의미이고, 모르는 값과의 비교는 모른다고 답하는 것이 정직하다. 우리는 그 정직함을 \"불편함\"으로 받아들이고, 자꾸 다른 답을 기대하다가 사고를 낸다.

세 가지만 의식적으로 다뤄도 사고의 대부분은 막을 수 있다. 첫째, NULL과의 비교는 오직 `IS NULL`로만 가능하며 다른 모든 연산은 UNKNOWN을 전파한다. 둘째, `NOT IN` 서브쿼리의 결과 집합에 NULL이 섞이면 그 쿼리는 항상 빈 결과를 낸다 — 이때는 `NOT EXISTS`로 옮기거나 서브쿼리에서 NULL을 명시적으로 걸러내야 한다. 셋째, `LEFT OUTER JOIN`을 했다면 \"왼쪽이 NULL일 수 있는\" 컬럼을 WHERE에 두는 순간 외부 조인이 내부 조인으로 변질된다 — 이런 조건은 반드시 ON 절로 옮겨야 한다. 이 세 가지가 NULL과 관련된 거의 모든 함정의 뿌리다.

NULL을 두려워할 필요는 없다. 오히려 NULL은 SQL이 \"모름\"이라는 상태를 명시적으로 표현하기 위해 만든 가장 정직한 장치다. 빈 문자열이나 0이나 -1로 대충 메우는 시스템보다, NULL을 가진 시스템이 훨씬 안전하다. 다만 그 정직함을 의식적으로 받아들이는 훈련이 필요할 뿐이다. 한 번 \"이 조건이 NULL을 만나면 어떻게 평가될까\"를 묻는 습관이 들면, NULL은 함정에서 도구로 바뀐다. 그리고 그 순간부터 우리가 만드는 쿼리는 비로소 모든 입력값에 대해 예측 가능한 답을 낸다.

시험장에서 NULL 관련 문제를 만나면 두 가지를 확인하자. 첫째, 이 표현이 \"3치 논리\"에서 어떤 값을 갖는가 — TRUE인가, FALSE인가, UNKNOWN인가. 둘째, 그 값이 WHERE를 통과하는가, 집계에 포함되는가, GROUP BY에 묶이는가. 이 두 가지만 잡으면 NULL 관련 거의 모든 문제가 풀린다.

이 다섯 편의 글에서 우리는 데이터베이스라는 시스템의 가장 깊은 기초들을 따라왔다. 왜 RDB가 생겼는지, 왜 정규화가 필요한지, ACID가 무엇을 지키는지, 윈도우 함수가 어떤 시선을 가져왔는지, 그리고 NULL이 어떻게 우리를 속이는지. 이 다섯 가지를 \"이해\"의 수준에서 잡고 나면, 시험을 위한 표와 암기법은 자연스럽게 따라온다. 그것이 이 칼럼들이 시험 직전이 아닌 처음 공부할 때 권해지는 이유다. 시험은 결국 \"이해한 사람\"이 빨리 풀게 되어 있다. 외운 단어는 잊혀지지만, 한 번 자리잡은 직관은 잊혀지지 않는다.
